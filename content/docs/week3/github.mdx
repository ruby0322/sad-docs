**GitHub** 是最常用的 Git 遠端托管與協作平台之一。第三週這一章專注在**儲存庫、分支推送、Fork 與 Pull Request（PR）**；將程式碼接上自動測與 **CI**（例如每次 PR 跑測試）則放在 **第十一週的 [GitHub Actions](/docs/week11/github)**，請在寫完測試後再接上。

---

## 為什麼需要 GitHub（或類似平台）？

- **中央式的協作界面**：Issue、PR、Review 留言都集中在網頁上，降低溝通成本。  
- **權限與分支保護**：可設定誰能 merge、`main` 是否一定要經過 PR。  
- **與課程銜接**：先熟練 PR 流程，第十一週再在 PR 上掛 **GitHub Actions**。

---

## Pull Request 是什麼？

**Pull Request**（在 GitLab 等平台常稱 **Merge Request**）代表：你希望把某個分支的變更**合併進**目標分支（例如 `dev` 或 `main`），並請團隊在合併前做 **Code Review**。

典型流程：

1. 從約定的基礎分支（例如 `dev`）開出功能分支（見 [分支策略](/docs/week3/branch-strategy)）。  
2. 本地開發、`commit`、`push` 到 GitHub 上的同名分支。  
3. 在 GitHub 開啟 **New Pull Request**：選擇「從哪個 branch 合併到哪個 branch」。  
4. 指定 Reviewer、填寫說明、依討論修改後，由維護者 **Merge**（或你自己在權限允許下完成）。

> Code Review 不只是挑錯，也是團隊對程式風格、測試與設計共識的累積。

## Fork 與上游（課程專案）

若課程提供範例儲存庫（如 SADo），常見作法是：

1. 在 GitHub **Fork** 到自己的帳號底下。  
2. **Clone** 自己的 Fork 到本機。  
3. 將**課程官方儲存庫**設為 `upstream`（若需要同步範本更新）：  
   ```bash
   git remote add upstream https://github.com/114-2-SAD/SADo.git
   git fetch upstream
   ```  
4. 在自己的分支上開發，並對 **自己的 Fork** 或**原專案**（若開放 PR）送出 Pull Request。

實際 URL 以課程公告為準；若組織仍是 `113-2-SAD`，請將 remote 改為對應網址。

## Issue 與任務追蹤

- **Issue**：記錄 bug、需求、討論決策。  
- 可與 PR 互相引用（例如 `Closes #12`），合併後自動關聯 Issue。

這些都與第十一週的 **CI** 無衝突：PR merge 前除了人工 Review，之後還可加上 **Actions 自動測試**（見 [GitHub Actions](/docs/week11/github)）。

## 小結

第三週在 GitHub 上要掌握的是：**遠端、分支、PR、Review 與合併策略**（搭配 [分支策略](/docs/week3/branch-strategy)）。  
**GitHub Actions** 留到第十一週，與 [測試計畫](/docs/week11/test-plan)、[Playwright](/docs/week11/e2e-tests) 一併完成 DevOps 實作。
